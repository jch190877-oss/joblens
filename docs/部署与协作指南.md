# 部署与协作指南

> 回答两个问题：
> ① 评委链接到底挂哪儿？
> ② 要不要上 GitHub？

## 〇、先记住一句话

**这个项目是纯静态站。**`pnpm build` 产出的 `dist/` 文件夹就是全部交付物——
没有后端、没有数据库、没有环境变量。

这意味着：**托管方是可以随时换的**。今天挂 A，明天想换 B，只要把 `dist/` 重新传一遍，
10 分钟就能换完，代码一行都不用改。所以下面的选型题不是"押注"，是"排序"。

## 一、评委链接怎么给

### 1.1 选型的真正标准

比赛场景和普通产品上线不一样，权重排序是：

| 权重 | 标准 | 为什么 |
| --- | --- | --- |
| ★★★★★ | **评委所在网络能稳定打开** | 打不开等于项目不存在，其他都是 0 |
| ★★★★☆ | 链接短、好念、能印在 PPT / 海报上 | 路演时评委是照着念的 |
| ★★★☆☆ | 推代码后能自动更新 | 避免"改了代码忘了重新传" |
| ★★☆☆☆ | 免费 / 便宜 | 学生项目 |
| ★★☆☆☆ | 有访问统计 | 复赛答辩时能说"已有 XX 次访问" |

### 1.2 关于 workbuddy

你提到的 workbuddy，我这边**无法确认它具体是哪个产品、是否支持托管静态站点并给出公网 URL**
——不同学校 / 平台叫这个名字的东西差别很大。所以给你一个**判断清单**，你拿它去问平台方或自己试：

> ✅ 满足以下 4 条，就可以用它作为**主链接**：
> 1. 能上传一组静态文件（一个文件夹，含 `index.html` + `assets/`），或能直接连 GitHub 仓库；
> 2. 给出的 URL 是**公网可访问**的（不是只在校园网 / 登录后才能看）；
> 3. URL **长期有效**，不会一周后过期（很多 AI 应用搭建平台生成的是临时预览链接，会失效）；
> 4. 支持**子路径部署**（URL 形如 `xxx.com/你的项目名/`）也能正常打开——这点很重要，因为校方平台常给子路径。

**如果满足**：用它做主链接完全没问题，甚至更好——它通常是最符合比赛要求、最不容易被质疑的渠道。
**如果不满足（尤其第 3 条）**：别赌，用下面 1.3 的方案，把 workbuddy 当展示辅助。

> 💡 落地建议：**主链接用稳定的一方，workbuddy 之类当作"过程演示"**。
> 评委真正要看的是产品，不是托管平台。

### 1.3 推荐的三种稳定方案

> ✅ **本项目的仓库与部署已经完成**：
> 代码在 <https://github.com/jch190877-oss/joblens>，
> 演示站是 <https://jch190877-oss.github.io/joblens/>。
> 下面 1.3 节保留为「换成你们自己的账号」时的操作参考。

#### 方案 A：GitHub Pages（推荐作为主链接，零成本 + 全自动）

仓库里已经写好了 `.github/workflows/deploy.yml`，推送即发布。

```bash
# 1. 在 GitHub 新建仓库（比如 joblens），不要勾选 README
git init
git add .
git commit -m "feat: 职镜 JobLens 前端 Demo 初版"
git branch -M main
git remote add origin https://github.com/<你的用户名>/joblens.git
git push -u origin main
```

然后在仓库里点两下：

1. **Settings → Pages → Build and deployment → Source** 选 `GitHub Actions`
2. 回到 **Actions** 标签，等第一次 workflow 跑完（约 1 分钟）

链接就是：`https://<你的用户名>.github.io/joblens/`

> 因为项目用了**哈希路由** + `base: './'`，放在 `/joblens/` 这种子路径下可以直接正常工作，
> 不需要任何额外配置。这也是当初特意选哈希路由的原因。

**优点**：免费、永久、推代码自动更新、评委能看出工程规范。
**注意**：国内访问 GitHub Pages 时快时慢，**务必实测**，并准备好备用链接。

#### 方案 B：Cloudflare Pages / Vercel（最省事，但要实测国内访问）

两个都是「连 GitHub → 自动部署 → 每个 PR 生成独立预览链接」。

| | Cloudflare Pages | Vercel |
| --- | --- | --- |
| 免费额度 | 无限静态请求 | 100GB/月 |
| 默认域名 | `项目名.pages.dev` | `项目名.vercel.app` |
| 国内访问 | 通常比 Vercel 稳，但仍需实测 | 经常不稳定 |
| 构建配置 | Build command: `pnpm build`<br>Output directory: `dist` | 自动识别 Vite |

> 两者都需要选 **Node 18+**，并把包管理器识别为 pnpm（有 `pnpm-lock.yaml` 会自动识别）。
> 如果 CI 报找不到 pnpm，把 Build command 改成 `npx -y pnpm@11 build` 即可。

**强烈建议**：这两个平台的 **PR 预览链接**功能，是团队协作里最值钱的东西——
每个 PR 一个独立 URL，产品组不用装环境就能点开看最新效果。

#### 方案 C：国内云静态托管（国内访问最稳，但要花钱/备案）

腾讯云 COS / EdgeOne Pages、阿里云 OSS、又拍云等。

- **优点**：国内访问速度快、稳定，答辩现场最不容易翻车。
- **代价**：需要实名认证；绑定自定义域名通常要 **ICP 备案**（备案要 1–3 周，现在开始准备可能来不及）。
- **注意**：各家的"默认域名"策略会变（有的会强制下载 html、有的限制 Referer），
  **部署前请以控制台当前说明为准**，别照旧教程操作。

> 如果时间紧张又想稳，可以先用平台给的**默认域名**（一般能直接访问），
> 不要为了好看去买域名 + 备案——**来不及，且有风险**。

### 1.4 我的具体建议（组合拳）

```
主链接   GitHub Pages          → 印在 PPT 首页 + 海报二维码
备用链接 Cloudflare Pages      → 万一主链接打不开，用短链跳转/现场备用
离线兜底 dist/ 打包进 U 盘      → 现场没网也能演示（用 pnpm preview 起本地服务）
```

**三个必须做的动作：**

1. **二维码**：把主链接生成二维码，印在 PPT 最后一页和海报上。评委扫码比输网址现实得多。
   在线生成即可（草料二维码等），或用本地工具，别把链接做成"请访问 xxx 点 com 斜杠 斜杠..."。
2. **短链**：如果主链接太长（`xxx.github.io/joblens-fe-2026/`），用一个短链服务跳转，
   现场念起来方便，也方便事后更换真实地址。
3. **至少两台设备、两种网络实测**：一台连 Wi-Fi、一台用 4G/5G，各打开一次。
   **不要在答辩前 10 分钟才第一次点链接。**

### 1.5 答辩现场的兜底方案（重要）

现场 Wi-Fi 出问题是常态。请提前准备：

```bash
pnpm build
# 把 dist 文件夹打包，拷进 U 盘
```

现场如果网挂了：

```bash
# 方式一：用仓库自带的静态服务器（推荐，零安装）
node scripts/serve.mjs dist 8080
# 打开 http://localhost:8080

# 方式二：如果你机器上有 Node
npx serve dist
```

> ⚠️ **千万不要直接双击 `dist/index.html`**。Chrome / Edge 会以 CORS 策略拦截
> `file://` 下的 ES module，页面直接白屏——这是最常见的现场翻车原因。
> 必须通过 `http://` 打开。

## 二、要不要上 GitHub

### 结论：要，而且越早越好

理由是三个具体问题，不是"工程规范"这种虚的：

1. **多人改同一个文件必然冲突。**没有版本管理，就会变成"谁最后存盘听谁的"，
   或者靠微信传 `index-最终版-2-真的最终版.zip`。
2. **没有回滚能力。**答辩前一天改崩了，Git 一条命令回到昨天的版本；压缩包只能祈祷。
3. **评委链接要能自动更新。**接了 GitHub Actions / Vercel 之后，
   推代码 → 链接自动变新，不会出现"演示的是旧版本"。

### 2.1 仓库设置（花 3 分钟，省两周的麻烦）

- **公开 / 私有**：建议**私有 + 邀请队友**。理由见 2.4 隐私提醒。
  如果比赛要求开源再改公开（一条命令的事）。
- **Settings → Collaborators**：把技术组所有人拉进来，别只留一个管理员。
- **Settings → Branches → Add branch protection rule**：保护 `main`，
  勾选 *Require a pull request before merging*。防止有人直接往主干推。
- **加一个 `.gitignore`**（已经有了）：`node_modules/`、`dist/`、`*.local` 都不进仓库。

### 2.2 分支策略（学生团队够用的最简版）

```
main          ← 永远可运行、可部署。只有 PR 合并能进
 └─ feat/xxx   ← 每人一个功能分支
 └─ fix/xxx    ← 修 bug
```

日常流程就三步：

```bash
git checkout -b feat/report-radar      # 开新分支
# ...改代码...
git add -A && git commit -m "feat(report): 五维评分改成雷达图"
git push -u origin feat/report-radar   # 推上去 → 开 PR
```

然后在 GitHub 上开 PR → 让另一个人点 Approve → 合并进 `main` → 自动部署。

> **关键收益**：如果接了 Vercel / Cloudflare，**每个 PR 会自动生成一个预览链接**。
> 产品组不用装 Node、不用会命令行，点链接就能看到改动效果，反馈快十倍。

### 2.3 提交信息规范（不用严格，但统一一下有好处）

```
feat: 新功能        fix: 修 bug        docs: 文档
style: 样式调整      refactor: 重构     chore: 杂项
```

例：`feat(deepdive): 追问支持示例填充按钮`

### 2.4 ⚠️ 隐私提醒（这条最重要）

访谈转录稿里有**受访者真实姓名、专业、年级、实习公司、具体项目细节**。
如果仓库设为公开，这些一旦推上去就是**永久公开、可被搜索引擎收录**，删都删不干净。

**必须遵守：**

- ❌ **不要**把 `访谈转录汇总/` 里的任何 `.docx` / `.txt` 放进仓库
- ❌ **不要**在代码、注释、commit message 里写真实姓名
- ✅ 仓库里统一用 `S01`–`S05` 代号 + `李同学 / 陈同学 / 冯同学` 这类化名
- ✅ 本仓库的 `src/data/demo.ts` 已经全部做过匿名化处理，可以直接用

> 另外：如果比赛要求提交"原始调研材料"，那应该走**单独的提交渠道**（加密压缩包 / 官方系统），
> 而不是塞进 GitHub 公开仓库。

### 2.5 如果 GitHub 访问不稳定

- **推代码慢**：配置代理，或 `git config --global http.postBuffer 524288000`
- **全程打不开**：国内可用 Gitee 作镜像仓库（`git remote add gitee ...`，一条命令双推），
  但 **Pages 自动部署还是建议用 GitHub**，因为 Gitee Pages 对个人已基本关闭。
- **只影响 CI**：本地 `pnpm build` 生成的 `dist/` 手动上传到任何一个静态托管都能用，
  不依赖 GitHub。

## 四、回滚到稳定版本

仓库里有一个标签 **`v0.1-demo`**，指向第一个「通过线上部署验证」的版本。任何时候改坏了都能退回来。

**① 只想看看旧版本长什么样（安全，不动代码）**

```bash
git checkout v0.1-demo     # 临时切过去
git switch main            # 看完切回来
```

**② 线上被改坏了，要一键恢复**

```bash
git checkout main
git reset --hard v0.1-demo
git push --force origin main
```

推送后 GitHub Actions 会自动重新部署，约 1 分钟线上恢复成稳定版。

> ⚠️ `--force` 会覆盖远端提交历史。只在 main 上确实是坏代码时使用，
> 并且先确认没有别人正基于这些提交开发，否则他们的工作会丢。

**③ 先看改了什么，再决定要不要回滚**

```bash
git log --oneline v0.1-demo..HEAD    # 稳定版之后又提交了什么
git diff v0.1-demo HEAD --stat       # 具体动了哪些文件
```

**④ 让 AI 从稳定版起一个新分支（推荐给 Codex 用）**

```bash
git fetch --tags
git checkout -b feat/xxx v0.1-demo
```

这样即使改坏了，`main` 也一直安全。

## 五、常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 页面白屏 | 直接双击 `index.html`（`file://` 被 CORS 拦） | 用 `pnpm preview` 或任意静态托管 |
| 部署后 404 / 资源加载失败 | 托管给了子路径，但 `base` 不是相对路径 | 本项目已设 `base: './'`，若改过记得改回来 |
| 刷新页面 404 | 用了 history 路由 | 本项目是哈希路由，不会出现；若改成 history 需配 rewrite |
| CI 报 pnpm 找不到 | workflow 没装 pnpm | 用仓库里的 `deploy.yml`，或 `npx -y pnpm@11 build` |
| `pnpm install` 报 `IGNORED_BUILDS` | pnpm 10+ 默认禁止依赖执行安装脚本 | 已在 `pnpm-workspace.yaml` 里用 `allowBuilds` 放行 esbuild |
| 字体 / 排版和设计稿不一样 | 系统缺字体 | 本项目只用系统字体栈，无需联网加载字体 |
