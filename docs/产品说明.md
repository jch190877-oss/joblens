# 职镜 JobLens · 产品说明

> 面向大学生求职场景的 AI 简历竞争力分析与优化平台
> 版本 v0.6 ｜ 更新 2026-11 ｜ 在线演示 <https://jch190877-oss.github.io/joblens/>

---

## 一、一句话定位

**职镜不替你编经历。它只做一件事：把目标岗位的要求逐条拆开，再把你真实做过的事，一条一条对上。对不上的地方，它不猜——它来问你。**

差异化的四个关键词：**岗位对齐 · 原文可查 · 反问补细节 · 事实安全**。

---

## 二、要解决的问题

### 2.1 从学生这一侧

| # | 痛点 | 典型表现 |
| --- | --- | --- |
| 1 | 不知道哪些经历该留、哪些该删 | 把所有做过的事都放上去，反而埋掉最相关的那条 |
| 2 | 写出来永远是「参与 / 协助 / 负责」 | 停在动作层，写不出规模、方法、结果，更写不出困难与解法 |
| 3 | 用 AI 改完，不敢确认哪句是真的 | AI 补出没做过的职责和数字，只能全信或全弃 |

三条其实是一个问题：**学生缺的不是文字能力，是「我做过的事对招聘者意味着什么」的判断依据。**

### 2.2 从招聘者这一侧

访谈 2 位正在做招聘的 HR 后，补充了三条学生自己判断不了的：

- **初筛先看硬性条件**，通过之后再比相关实习经历的匹配度
- 招聘者的真实决策函数是**「上手快、降低培养成本」**，不是「你优不优秀」
- **「知名企业实习最大的坑，就是把平台当成个人能力」**——平台光环不等于个人贡献

## 三、目标用户与场景

- **核心用户**：大一至大四、已有社团 / 课程项目 / 竞赛 / 家教 / 短期实习经历，但不知如何针对岗位呈现的早期求职者。
- **典型场景**：第一次投互联网 / 产品 / 运营岗；用同一份简历海投几十家；想转方向但不知道怎么把现有经历「翻译」成目标岗位的语言。
- **首批岗位**：教培教师、互联网后端 / IT 审计、产品运营。选择标准是样本易获取、JD 结构清晰、经历可核验。
- **边界**：已经具备强背景、能独立完成岗位定制的学生，不是首期服务对象。

## 四、产品机制

```
① 建经历库    把做过的事原样倒进来，允许口语、允许粗糙
       ↓
② 拆解 JD     硬性条件 / 核心职责 / 加分项，各带权重与规则编号
       ↓
③ 逐条对照    四态判定：满足 / 部分满足 / 不满足 / 待核实，每条指向简历原文
       ↓
④ 反问深挖    针对缺口提具体问题，你答事实，系统组织成证据
       ↓
⑤ 改写取舍    采纳 / 忽略 + 事实状态标记 + HR 视角预览 → 导出投递版
```

四个页面对应这条链路：`分析工作台` → `对照报告` → `经历深挖` → `改写工作台`，另加 `方法论` 说明研究依据。

## 五、评价体系（本产品的核心）

### 5.1 总分：可复算的加权模型

```
总分 = Σ(归一化权重_i × 达成度_i)

达成度：满足 1.0 · 部分满足 0.5 · 待核实 0.2 · 不满足 0
硬性条件不满足 → 门槛优先，总分封顶 40
```

- 权重在案例内**归一化到 100**
- 每条要求的贡献逐行可见：规则编号 / 要求 / 权重 / 判定 / 达成度 / 得分
- 报告页可展开「总分怎么算出来的」，任何人可以指出「哪一条判定不对、哪一条权重该改」

> 这是本产品与「AI 给你打个分」最根本的区别：**分数不是一个黑箱输出，而是一张可以逐行核对的表。**

### 5.2 四个诊断维度：由判定及自检算出

| 维度 | 计算来源 |
| --- | --- |
| 门槛达成 | 硬性条件组内加权达成度 |
| 相关经历 | 核心职责组内加权达成度 |
| 加分储备 | 加分项组内加权达成度 |
| 表达与结构 | 投递前检查扣分（必须补 −20 / 注意 −8） |
| 投递稿事实风险（单独展示） | 待补数字与已拦截新增事实的数量，不给求职者扣分 |

维度是**分组视图**，用于定位「差在哪一层」，不参与总分合成——两者口径不同，界面上也明确标注。

### 5.3 权重从哪来

| 阶段 | 来源 | 状态 |
| --- | --- | --- |
| 初始权重 | 学生访谈编码 | 已完成 |
| HR 校准 | 2 位 HR 的定性说明（个人贡献 15%→20%、可信度 5%→7%） | 已完成 |
| AHP 正式标定 | 2 位 HR 做 5×5 成对比较，求特征向量并检验 CR | **工具已就绪，尚未采集** |

AHP 工具见 `docs/ahp/`：`问卷.html` 给 HR 填（实时算权重与 CR），`ahp.py` 做合并与复算，`--self-test` 可验证算法。

## 六、事实安全机制

三件事，缺一不可：

**① 四态判定，而不是二元对错**
「满足 / 部分满足 / 不满足 / 待核实」。**待核实**是一等公民——查不到证据不等于造假，只是还缺信息。

**② 三道闸**

| 闸 | 规则 |
| --- | --- |
| G1 原文锚定 | 每条改写必须能指回简历原文，指不回去的不生成 |
| G2 数字留空 | 模型不生成任何量化数字，只留占位符由用户填真实值 |
| G3 禁用表述 | 「保证录用」「包过」等在导出前被规则库拦截 |

**③ 每条建议标注事实状态**
改写卡上明确标记：**原文可证 / 需你补数字 / 已拦截（AI 想加的、但你没有的事实）**。默认只有「原文可证」的条目进入投递版。

## 七、研究基础

共 **7 份访谈**，两种视角：

| 来源 | 人数 | 覆盖 |
| --- | --- | --- |
| 学生访谈（S01–S05） | 5 | 教培、互联网技术、市场营销、产品运营；5 份逐字转录稿 |
| HR 访谈（HR01–HR02） | 2 | 外籍人员子女学校招聘；教培 / 多行业招聘（含校招社招与猎头） |

**HR 带来的两个反直觉结论：**

- 「平台不等于个人能力」——名企实习可能是光环，也可能是陷阱
- 「经历类型没有高低之分」与另一位 HR 的「实习 > 技能/竞赛 > 校园活动」**明确冲突**

**我们对分歧的处理**：不调和成一句结论，而是做成**可调权重**，并在方法论页把两方原话并列展示。

### 必须说清楚的边界

1. 2 份 HR 访谈均为**记录整理稿**，非逐字转录
2. 两位 HR 均来自**教育行业**，不能外推到全行业
3. 两位的 **Q20–Q24（A/B 简历对比、AI 参与看法、AI 评价维度、三条建议）全部未作答**——因此产品中关于 AI 价值的判断属于**我们的推断**，不是 HR 的结论
4. 尚未做与 HR 判断的一致性检验（kappa），因此无法声称「系统的判定已通过专家验证」

## 八、产品现状

### 8.1 已经跑通的（前端原型）

- 6 个页面完整链路，含首屏 3 秒自我演示
- 3 个来自访谈的匿名化案例（产品运营 / IT 审计 / 教培教师）
- 4 态判定 + 原文依据 + 规则编号
- 总分与四个诊断维度**全部由判定实时计算**
- 经历结构加权、平台归属判定、投递前自检、改写前后对照
- 事实安全三道闸的界面呈现
- 部署：GitHub Actions 自动构建，推送即上线

### 8.2 尚未接入的

| 缺口 | 说明 |
| --- | --- |
| AI 分析链路 | JD 拆解、反问生成、事实校验器目前是**预置演示**，不是真实模型调用 |
| 文件解析 | 简历 PDF / 图片解析未做。单条练习可粘贴岗位要求和经历，并手动补充事实。 |
| 账号与存储 | 无登录、无历史记录 |
| AHP 实际采集 | 工具就绪，数据未采集 |
| 一致性检验 | 未做，因此暂无 kappa 指标 |

> 演示页中所有分数、判定、追问均为预置数据。这一点在产品内也明确标注。

### 8.3 技术选型

Vite 6 + React 18 + TypeScript + Tailwind CSS 4；手写哈希路由；`base: './'`，可部署在任意静态托管；除 React 外无运行时依赖。

## 九、与同类方案的区别

| 能力 | 通用大模型 | 模板 / 改写平台 | 招聘平台 AI | 职镜 |
| --- | --- | --- | --- | --- |
| JD 拆到条目级 | 部分 | 弱 | 强 | 强 |
| 每条建议可回溯原文 | 弱 | 弱 | 弱 | 强 |
| 拦截 AI 新增事实 | 弱 | 弱 | 部分 | 强 |
| 主动反问补细节 | 部分 | 无 | 无 | 强 |
| 四态判定替代单一分数 | 无 | 无 | 无 | 强 |
| 总分可逐行复算 | 无 | 无 | 无 | 强 |

一句话：**通用模型负责「写得好看」，招聘平台负责「筛得快」，我们做中间那个一直缺位的东西——可核对、可解释、不编造。**

## 十一、伦理与合规

- 平台输出为**求职辅助建议**，所有结论均指向简历原文与规则编号；录用判断由招聘主体独立完成
- **不作录用承诺**，不使用「提升录用率 XX%」这类无法验证的表述
- 访谈材料统一匿名化，使用 `S01–S05 / HR01–HR02` 代号；原始转录稿不进入公开仓库
- 简历涉及个人信息，遵循最小化采集、用途限定、可删除原则；当前版本不收集、不上传任何用户数据
- 涉及 AI 局限性的判断在界面与方法论页均显式标注，不夸大能力
